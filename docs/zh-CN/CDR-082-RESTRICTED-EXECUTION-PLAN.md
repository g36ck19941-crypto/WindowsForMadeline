先给后续原版小测试建一个“受限制的试验隔间”：不是出事后才记录，而是提前阻止不该发生的访问。本次没有新增角色、动画或玩法，没有改变 GOAL.md 的完整项目目标。

起点为 `codex/cdr-082-local-compile-probe` 分支、提交 `4b531fd368e318ac9c7cb57627bf338a8d210694`，开始时工作树干净。现有证据只证明编译和自有测试进程监控；没有证明原版能安全运行。缓存 XNA 的两个混合库，各仍有2个未分类原生函数体、11处间接调用。此次未加载或执行原版/XNA，过去的测试结果不是此次隔离已经有效的证据。

## 建议选择

首先评估 **AppContainer 权限隔离 + 启动前限制 + Job Object 进程管理**。这是候选，不是已经建好的沙箱。旧版 x86 .NET Framework 4.7.2 和混合原生 XNA 是否适用，仍未知。

任何一项必需限制做不到就停止；不改成普通进程重试、不偷偷放宽权限、不替换成 FNA、不改原版行为代码来凑通过。

AppContainer 能限制资源权限，但部分键鼠访问仍可用，文件读取也并非完全白名单，因此不能单独满足我们的要求。[微软隔离说明](https://learn.microsoft.com/en-us/windows/win32/secauthz/appcontainer-isolation)。

Job Object 能管理一组进程的资源与退出；其界面限制只针对特定操作，不是全面的文件、网络、窗口或设备屏障。[进程组说明](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)、[界面限制说明](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_ui_restrictions)。

禁止 Win32k 系统调用可作为 GUI 限制候选，但不是音频、手柄或网络的万能开关；要先用自有代码验证兼容性。“只审计”不等于阻止。[微软进程限制说明](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-process_mitigation_system_call_disable_policy)。

## 每一块怎样限制，哪些还没解决

以下全部是设计要求，**尚未实现或验证**。

| 要保护的部分 | 拟采用的限制 | 放行原版前必须证明 |
| --- | --- | --- |
| 游戏目录、个人文件、注册表 | 子进程不配置游戏路径；独立身份、精确权限；只读输入暂存区和私有临时区 | 检查实际权限，包括普遍允许读取的文件、链接和继承句柄；使用自造越界文件验证拒绝，不碰游戏目录 |
| 运行依赖 | 已授权文件的身份/哈希清单，固定查找位置 | 不默许从系统GAC、PATH、当前目录补库；未列依赖即停止。操作系统/CLR正常加载所需文件也要明确范围，元数据授权不是运行授权 |
| 网络和远程通信 | 不授予网络能力，不提供网络代理或继承连接 | 自有本地测试证明禁止访问被拒绝；父进程报告通道不能替子进程执行任意请求 |
| GUI与真实输入 | 启动前禁止Win32k调用，不接入交互桌面；另行设计设备限制 | 必须在任何库初始化前生效；窗口、键鼠、XInput/手柄分别验证。隐藏桌面、CreateNoWindow本身不够 |
| 音频、Steam及设备 | 不提供服务代理、设备句柄；设备/库限制仍需细化 | 没有一个现成开关能保证覆盖所有API；Steamworks以前仅准作编译元数据。只禁止某个DLL名字不够，未知访问路线不能放行 |
| 其他进程 | 私有Job，不准脱离，限制子进程数量，最小化句柄继承，不提供启动代理 | 用自有代码验证子进程、逃逸与父进程退出；限制要在恢复执行前设置；只清理自己创建的对象，不能按名称/PID批量结束其他程序 |
| 商业数据与输出 | 仅使用明确授权的忽略缓存作为只读输入；每轮私有临时区；只输出摘要 | 日志、Git及上传不得含源码、IL、像素或音频；子进程日志视为不可信，限长和过滤；不写输入或安装目录 |

不能保证任意代码“绝对零副作用”，系统漏洞和未覆盖的设备/加载路径也是风险。尤其目前**没有已验证的完整禁输入、禁音频配置**，因此这份方案不允许开始运行原版。

## 启动顺序和日志

父进程只持有本轮自己的句柄、标识和临时目录。拒绝链接、哈希变化、意外参数及未经授权的文件，不给整个仓库或游戏目录的访问权。增加依赖复制需要另行授权。

限制必须早于目标库加载和模块初始化。拟采用“先挂起创建、配置Job及检查实际策略、再恢复”的顺序；任何配置失败就结束自有子进程，不加载目标。原版库不进入父进程，不提供任意Shell、命令、目标路径或加载钩子。

日志阶段拟为：策略核对 → 自有探针就绪 → 依赖核对 → 请求目标加载 → 目标加载完成 → 输入上下文就绪 → 预设步骤结束 → 清理确认。记录轮次、策略版本、实际限制、最后阶段、耗时、退出码、可获得的异常链/HResult、超时/输出超限原因和清理结果。没来得及打印日志仍属未知，不能当成没有副作用。保留已有日志限长和超时设计，但重新验证兼容性；阶段名称不证明角色生成、显示或可动。

卡死或原生退出由父进程和自有Job处理，必须确认所有自有进程已退出。临时目录、配置身份或ACL回滚要有精确归属记录，失败需报告。不得修改全局权限、防火墙或系统策略，也不能递归删除宽泛目录。

## 备选方案

普通子进程、受限令牌或低完整性单独使用都不足；监控也只是诊断。

不共享宿主文件、网络、输入、音频和设备的无界面虚拟机，可作为独立备选研究。但宿主设施、客体依赖和兼容性均未确认，建立环境需要新的授权。

Windows Sandbox **不是当前“不启动GUI”的执行路线**。它支持关闭网络、只读共享目录；AudioInput控制麦克风输入，并不能证明音频播放被禁。本次不启动它，也不生成可执行的 `.wsb` 配置。[微软Sandbox配置说明](https://learn.microsoft.com/en-us/windows/security/application-security/application-isolation/windows-sandbox/windows-sandbox-configure-using-wsb-file)。

## 分类、顺序与授权门禁

1. **当前：仅方案交付。** 不生成运行代码/配置，不跑进程测试，不检查本机设施，不改策略或权限，不访问安装目录，不加载原版。
2. **下一步候选：只读可行性核对，需新授权。** 限定Windows版本/架构、现有安全与进程设施、获准CLR能力。逐项给出支持/未知/不支持及具体实现范围，不开GUI、不加载库、不安装下载、不扫描游戏目录或递归查依赖，不启用系统功能。
3. **实现和自有拒绝测试，需单独授权。** 先列文件范围、可恢复的身份/ACL改动、API尝试与合成文件。可能产生窗口、访问实时输入/音频/网络或改变系统状态的测试，需要明确权限及前置保证，不能认为“预计失败”就没有副作用。不运行原版/XNA/Steam。
4. **仅原版加载可行性，需单独授权。** 先通过限制有效性与兼容性门禁，再核对缓存清单和初始化边界。没有Player、素材、设备或正常Engine启动；缺依赖、缺限制或出现异常效果就停止。
5. **原版预设输入/时间连接，需单独授权。** 只用缓存和原版输入缓冲；角色、素材、离屏呈现另定范围，真实桌面可见验收仍在更后面。

验收方案不等于授权第2—5步，也不自行将CDR-082改为accepted。可行性核对要有固定范围，不无限追查Windows依赖。
