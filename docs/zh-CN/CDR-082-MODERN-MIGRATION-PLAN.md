# 本次更新：不依赖旧框架的迁移方案

2026-10-06，Primary，基线7ce988e。本次只设计，没有新增运行功能。

## 它在项目中的作用

目标仍然是让原版角色和交互物品在我们的桌面程序里工作，但正式功能不能依赖旧.NET Framework。

建议路线：**保留原版“怎么运动、怎么碰撞”的逻辑，重新连接“从哪里拿时间、输入、场景和图像”的接口，在现代运行环境里重新编译。**不是重新猜一套玩法，也不是把原版放进旧框架辅助程序里绕过去。

这条路线尚未证明可行。原版依赖较多，有些接口可能需要改造；必须先列清楚，再决定具体方案。本轮没有修改或读取原版源码，也没有选定新的替代库。

## 哪些东西可保留，哪些要重新处理

| 部分 | 本方案如何处理 |
| --- | --- |
| 角色运动、碰撞、状态与物品规则 | 优先保留原版逻辑；不能用自写替身解决编译错误 |
| 时间和输入 | 利用现有预设输入/固定时间工具，连接原版真正使用的接口；自己的输入记录不等于原版已消费输入 |
| 场景和角色初始化 | 找出角色真正需要的Level、边界、设置等条件，不启动完整引擎来凑环境 |
| 框架类型和绘图接口 | 先查所需类型和操作，再选适配策略；不能偷偷换XNA或直接采用旧运行库 |
| 素材目录、动画呈现、匿名桌面几何 | 现有独立工具保留，后续与原版状态连接；不能拿已有合成演示冒充原版角色 |
| Steam、音频、真实输入、窗口等服务 | 离线阶段禁止；若某项是行为必需条件而无法隔离，应停下报告，不能随便空实现后说成功 |

“现代环境”也不是已经可用的结论：此前自有.NET8受限启动仍有失败记录，需要独立排查。我们既不认定换框架就能解决，也不为了启动成功放宽限制。

## 后续按什么顺序做

1. **M1：列清单。**只读现有恢复缓存，找出角色所需代码、类型、初始化和平台调用。详细信息留本地，公开报告只有分类统计。下一步建议先做这一项，需要你授权。
2. **M2：设计接法。**确定保留哪些原版逻辑、哪些平台接口需要适配，以及现代目标和候选依赖。新依赖审查或源码转换须另行明确范围。
3. **M3：只编译。**如需转换，先获准在独立本地副本里做，保留原始恢复缓存，记录每处变更。检查生成物不依赖旧框架，不运行。
4. **M4：测试自有宿主。**先证明现代宿主能在限制下启动、报告就绪和清理退出。它通过也不等于原版通过。
5. **M5：接原版输入和时间。**经单独授权后，先做不创建角色的小测试，观察原版逻辑是否真的吃到了预设输入。
6. **M6：创建角色并产生离屏图像。**连接场景、资源和动画；分别验证动作和像素，不启动完整游戏。资源与运行范围另行授权。
7. **M7：桌面与物品。**再接桌面环境、逐个物品；可见窗口和实时输入仍需单独验收授权。

编译通过不能跳过启动和行为检查。某个关键依赖未知就停在对应步骤，不继续增加模拟功能把测试做绿。

## 原版逻辑怎么保证不被乱改

原始恢复缓存保持不变。如果必须适配源码，先提交明确的修改范围，经授权后只在另一个Git忽略的本地副本做，并记录来源哈希和变更。

运动数值、判断顺序、取整、碰撞规则不能在“换接口”时偷偷改变。独立测试确认行为之前，只能说“迁移尚未验证”，不能说已经还原。以后获准做原版对照测试时，它也只能是测试，不成为产品依赖。

反编译源码、修改后的商业派生文件、素材和生成的商业派生库都不上传。GitHub只接收自有工具、适配合同、合成测试和不含商业内容的汇总。

## 如何发现问题

后续每次验证应能看见：用的是哪次迁移、哪些来源/引用、实际运行环境、停在哪一步、哪个tick、原版有没有消费输入、请求了哪个平台服务、进程是否清理。监控器报错与子进程异常分开，实际退出码与最后调试事件分开。缺失记录不能当通过，公开日志不放源码、原始素材或内存转储。
